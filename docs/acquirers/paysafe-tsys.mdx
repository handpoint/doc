```kotlin
        api = HapiFactory.getAsyncInterface(this, this, credentials)

        val device = Device("Terminal", "1", "", ConnectionMethod.ANDROID_PAYMENT)
        api.connect(device)
    }

    override fun currentTransactionStatus(info: StatusInfo, device: Device) {
        if (info.status == StatusInfo.Status.InitialisationComplete) {
            // SDK ready — safe to call api.sale(), api.refund(), etc.
        }
    }

    override fun endOfTransaction(result: TransactionResult, device: Device) { /* handle result */ }
    override fun transactionResultReady(result: TransactionResult, device: Device) { /* handle recovered result */ }
    override fun connectionStatusChanged(status: ConnectionStatus, device: Device) { /* update UI */ }

```

:::caution Wait for InitialisationComplete
Do not call any financial operation before `currentTransactionStatus` fires with `StatusInfo.Status.InitialisationComplete`. Calling earlier results in `CommandNotAllowed`.

## Sale {#sale}

### What this does
Authorises and captures a card-present payment in a single step.

### When to use it
Use for standard retail and hospitality transactions where the cardholder is present and the amount is known before the transaction starts. Do NOT use when the final amount may change after authorisation — use Pre-Authorization instead.

### Implementation notes

1. The terminal handles EMV chip, contactless, and magnetic stripe automatically — you do not specify the card entry method.
2. The SDK returns an `OperationStartResult` synchronously with a `transactionReference`. The actual result arrives asynchronously via the events listener/callback.
3. Always store the `transactionReference` immediately — you need it for any subsequent reversal.
4. Amount is in the smallest currency unit (cents/pence). `1000` = $10.00 USD.

:::note PAYSAFE
Paysafe uses TSYS + TNS routing infrastructure. MOTO, partial reversal, and pre-authorization are not available. Tip adjustment forthcoming. Tokenization: single-use Paysafe token — requires merchant onboarding by Paysafe/Handpoint before use. Interac transactions follow TNS void-only rules — see Interac VOID guide.
:::

## Refund {#refund}

### What this does
Returns funds to a cardholder's account, either linked to a specific original transaction or as a standalone credit.

### When to use it
Use for returning goods or services after settlement has occurred. For cancellations before settlement, use Reversal instead — it is faster and does not incur interchange fees. Partial refunds (amount less than original) are supported at the protocol level for all acquirers.

### Implementation notes

1. **Linked refund** (recommended): includes `originalTransactionId` — the gateway validates the original transaction and caps the refund at the original amount plus any tip.
2. **Unlinked refund**: omit `originalTransactionId` — sends a standalone credit. Some acquirers restrict unlinked refunds; check your acquirer agreement.
3. Amount is in the smallest currency unit. Partial refund: set `amount` less than the original transaction amount.
4. The cardholder's card must be present for card-present refunds.

:::note PAYSAFE
Paysafe uses TSYS + TNS routing infrastructure. MOTO, partial reversal, and pre-authorization are not available. Tip adjustment forthcoming. Tokenization: single-use Paysafe token — requires merchant onboarding by Paysafe/Handpoint before use. Interac transactions follow TNS void-only rules — see Interac VOID guide.
:::

## Reversal {#reversal}

### What this does
Voids a sale before settlement, returning the full authorised amount to the cardholder without incurring interchange fees.

### When to use it
Use when a sale needs to be cancelled before the batch closes. This is always preferable to a refund for same-day cancellations — faster and fee-free. Do NOT use after settlement — send a Refund instead.

### Implementation notes

1. Reversal only works on the current open batch. Once the batch closes (auto or manual), only a refund is possible.
2. Full amount only — partial reversals are a separate operation (`partial-reversal`), supported only on TSYS US.
3. The original terminal must be connected. The reversal is sent to the same terminal that processed the original sale.
4. For Interac card transactions (TNS / TSYS + TNS): the only post-sale operation available is VOID (card must be present). Show a VOID button, not Refund or Reverse, for Interac transactions in your UI.

:::note PAYSAFE
Paysafe uses TSYS + TNS routing infrastructure. MOTO, partial reversal, and pre-authorization are not available. Tip adjustment forthcoming. Tokenization: single-use Paysafe token — requires merchant onboarding by Paysafe/Handpoint before use. Interac transactions follow TNS void-only rules — see Interac VOID guide.
:::

## Paysafe Token {#tokenization}

### What this does
When a card-present sale is processed through Paysafe, Handpoint returns a **Paysafe single-use token** in the transaction result. This token represents the card used at the terminal and can be submitted to Paysafe's Token Vault to create a reusable card-on-file token for future card-not-present (eCommerce) charges — without requiring the cardholder to re-enter their card details online.

This bridges card-present and eCommerce flows: a merchant can onboard a customer in person, store their card details securely in Paysafe's vault, and use the stored token for subsequent online charges (subscriptions, top-ups, deferred billing, etc.).

### When to use it
- Subscription or membership businesses that take the first payment in-person and charge recurring online
- Marketplaces that want to register a card on file after a POS transaction
- Any flow where a card-present sale should also authorise future card-not-present charges

### Requirements
- Merchant must be onboarded for the Paysafe Token Vault by Paysafe and Handpoint — contact your Handpoint integration manager to enable this.
- The token is single-use: it must be exchanged with Paysafe's Token Vault API immediately after the sale to create a reusable multi-use token.
- Standard Paysafe card-present onboarding is required in addition to Token Vault enablement.

### Implementation notes

1. Process a standard card-present sale as normal — no extra parameters needed on the Handpoint side.
2. Inspect the `TransactionResult` for the `paysafeToken` field — this is the single-use token issued by Paysafe.
3. Submit that token to the [Paysafe Token Vault API](https://developer.paysafe.com/en/payments/token-vault/) to create a reusable `paymentHandleToken`.
4. Store the `paymentHandleToken` against the customer record — use it for all future eCommerce charges via Paysafe's Payments API.
5. Tokens expire if not exchanged promptly — perform the Token Vault call synchronously in your `endOfTransaction` / result callback.

The response includes a `paymentHandleToken` — store this and use it for all future card-not-present charges. Refer to [Paysafe's Token Vault documentation](https://developer.paysafe.com/en/payments/token-vault/) for the full API reference and authentication setup.

## Transaction Result & Recovery {#txn-result}

Every financial operation is asynchronous — the result is never returned synchronously. This section explains how to receive, store, and recover results for each integration path, and what timeouts to design around.

<Tabs groupId="integration-path">
<TabItem value="cloud-api" label="Cloud API">

### Option 1 — Push notification (callbackUrl)

Include `callbackUrl` and `token` in your transaction request. When the terminal completes the transaction, the result is POSTed to your URL:

```http
POST https://your-server.example.com/handpoint/result
Content-Type: application/json
AUTH-TOKEN: <your-token-value>
AUTH_TOKEN: <your-token-value>

{ "finStatus": "AUTHORISED", "type": "SALE", "totalAmount": 1000, ... }
```

- The body is the full [Transaction Result](/reference/transaction-result-object) object.
- `token` is **not** in the body — it is in the `AUTH-TOKEN` and `AUTH_TOKEN` headers. Validate it on your server to authenticate the request.
- `"recoveredTransaction": true` means the delivery used the retry loop (first attempt failed).
- Respond with any `2xx` status to stop retries.

**Retry schedule:** every 5 seconds for the first 100 seconds, then exponential backoff (8s → 16s → 32s → …).

### Option 2 — Poll for result

If `callbackUrl` is omitted, the initial `POST /transactions` response includes a `transactionResultId`. Poll until you get a non-204:

```http
GET https://cloud.handpoint.com/transaction-result/0821032398-1628774190395
ApiKeyCloud: YOUR_MERCHANT_API_KEY
```

| Response | Meaning |
|---|---|
| `204 No Content` | In progress — retry in 3–5 seconds |
| `200 OK` | Complete — body contains the full Transaction Result |

### Option 3 — Query by transactionReference

At any time, query the gateway directly using the `transactionReference` you provided at transaction start. Note the **different base domain**:

```http
GET https://transactions.handpoint.com/transactions/{transactionReference}/status
ApiKeyCloud: YOUR_MERCHANT_API_KEY
```

Use `/status/all` to retrieve the full operation chain (sale + any linked refunds/reversals). See [Transaction Recovery & Status](/reference/transaction-recovery) for the full selector reference and `IN_PROGRESS` / `UNDEFINED` handling.

### Timeouts

The terminal can legitimately take up to **~340 seconds** in worst-case fallback paths (contactless retries → chip retries → swipe → PIN retries). Set your active-recovery timeout to **360 seconds** from request send time. After that, query `/status` once more — if still unresolved, flag for manual reconciliation. Do not auto-retry with the same `transactionReference`.

### Primary result — `endOfTransaction`

All financial operations return their result via this callback:

```kotlin
override fun endOfTransaction(result: TransactionResult, device: Device) {
    when (result.finStatus) {
        FinancialStatus.AUTHORISED -> {
            // Store result.transactionID — required for reversal
            // Store result.transactionReference — required for status queries
            println("Authorised: ${result.authorisationCode}")
        }
        FinancialStatus.DECLINED   -> println("Declined: ${result.statusMessage}")
        FinancialStatus.CANCELLED  -> println("Cancelled by cardholder")
        FinancialStatus.UNDEFINED  -> {
            // Gateway may or may not have processed — do NOT retry
            // Query via hapi.getTransactionStatus(transactionReference)
        }
        else -> println("Status: ${result.finStatus}")
    }
}
```

### Recovery — `transactionResultReady`

If your app missed an `endOfTransaction` (crash, restart), the SDK delivers the pending result here on reconnect:

```kotlin
override fun transactionResultReady(result: TransactionResult, device: Device) {
    // Handle identically to endOfTransaction
    processResult(result)
}
```

### Gateway query — `getTransactionStatus`

Query the gateway for the current status of any transaction using its `transactionReference`:

```kotlin
val sent = hapi.getTransactionStatus("2bfde1fc-23b1-4c67-93d9-1d4a557f4d4f")
// Result arrives via endOfTransaction
```

### Timeouts

The SDK's `app-side` transaction timeout is 240 seconds (4 minutes). The terminal can take up to ~340 seconds in worst-case paths. Use the `currentTransactionStatus` callback to update your UI during processing:

```kotlin
override fun currentTransactionStatus(info: StatusInfo, device: Device) {
    when {
        info.status == StatusInfo.Status.InitialisationComplete -> { /* ready */ }
        else -> updateStatusLabel(info.message)  // e.g. "Waiting for card", "Authorising..."
    }
}
```

Results arrive via the persistent `eventHandler` registered during initialization. Listen for `endOfTransaction` (final result) and `transactionResultReady` (recovered result on Android):

```javascript
handpoint.eventHandler(
  function(event) {
    if (event.event === "endOfTransaction") {
      const result = event.data.transactionResult;
      console.log("[HP] endOfTransaction", result.finStatus, result.totalAmount);

      if (result.finStatus === "AUTHORISED") {
        storeResult(result);
      } else if (result.finStatus === "UNDEFINED") {
        // Do not retry — query status manually
        flagForReconciliation(result.transactionReference);
      }
    }

    if (event.event === "transactionResultReady") {
      // Recovered pending result (Android only)
      processResult(event.data.transactionResult);
    }

    if (event.event === "currentTransactionStatus") {
      updateStatusUI(event.data.info.message);
    }
  },
  function(error) { console.error("Event error", error); }
);
```

## Validation {#validation}

Before going live, step through the following scenarios on your integration. Use a TEST/DEMO merchant or staging device — all amounts process as approved except specific trigger amounts. See [Development Hardware](/reference/development-hardware) for trigger amounts.

<Tabs groupId="integration-path">
<TabItem value="cloud-api" label="Cloud API">

| Scenario | How to test | Pass condition |
|---|---|---|
| **Happy path** | Send a sale for a non-trigger amount with `transactionReference` | `finStatus: AUTHORISED` delivered to `callbackUrl` or polled result |
| **Declined** | Use the `DECLINED` trigger amount | `finStatus: DECLINED` with no charge |
| **Duplicate prevention** | Send the same `transactionReference` twice | Second request rejected or deduplicated — only one charge |
| **Callback unreachable** | Send with `callbackUrl` pointing to a server that returns 500 | Verify retries fire (5s interval for 100s, then backoff); result eventually delivered on 2xx |
| **Poll fallback** | Send without `callbackUrl`; poll `GET /transaction-result/{id}` | 204 until complete, then 200 with result |
| **UNDEFINED recovery** | Kill network mid-transaction; let it time out | `finStatus: UNDEFINED` returned; verify you query `/status` and do not auto-retry |
| **Status query** | After an AUTHORISED transaction, query `GET /transactions/{ref}/status/all` | Full chain returned with correct amounts |
| **Network drop + reconnect** | Start a transaction; drop your server's network; reconnect after 30s | Result delivered on retry after reconnect |
