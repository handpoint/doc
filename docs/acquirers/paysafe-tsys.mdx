## Sale

### What this does
Authorises and captures a card-present payment in a single step.

### When to use it
Use for standard retail and hospitality transactions where the cardholder is present and the amount is known before the transaction starts. Do NOT use when the final amount may change after authorisation — use Pre-Authorization instead.

### Implementation notes

1. The terminal handles EMV chip, contactless, and magnetic stripe automatically — you do not specify the card entry method.
2. The SDK returns an `OperationStartResult` synchronously with a `transactionReference`. The actual result arrives asynchronously via the events listener/callback.
3. Always store the `transactionReference` immediately — you need it for any subsequent reversal.
4. Amount is in the smallest currency unit (cents/pence). `1000` = $10.00 USD.

:::note PAYSAFE
Paysafe uses TSYS + TNS routing infrastructure. MOTO, partial reversal, and pre-authorization are not available. Tip adjustment forthcoming. Tokenization: single-use Paysafe token — requires merchant onboarding by Paysafe/Handpoint before use. Interac transactions follow TNS void-only rules — see Interac VOID guide.
:::

## Refund

### What this does
Returns funds to a cardholder's account, either linked to a specific original transaction or as a standalone credit.

### When to use it
Use for returning goods or services after settlement has occurred. For cancellations before settlement, use Reversal instead — it is faster and does not incur interchange fees. Partial refunds (amount less than original) are supported at the protocol level for all acquirers.

### Implementation notes

1. **Linked refund** (recommended): includes `originalTransactionId` — the gateway validates the original transaction and caps the refund at the original amount plus any tip.
2. **Unlinked refund**: omit `originalTransactionId` — sends a standalone credit. Some acquirers restrict unlinked refunds; check your acquirer agreement.
3. Amount is in the smallest currency unit. Partial refund: set `amount` less than the original transaction amount.
4. The cardholder's card must be present for card-present refunds.

:::note PAYSAFE
Paysafe uses TSYS + TNS routing infrastructure. MOTO, partial reversal, and pre-authorization are not available. Tip adjustment forthcoming. Tokenization: single-use Paysafe token — requires merchant onboarding by Paysafe/Handpoint before use. Interac transactions follow TNS void-only rules — see Interac VOID guide.
:::

## Reversal

### What this does
Voids a sale before settlement, returning the full authorised amount to the cardholder without incurring interchange fees.

### When to use it
Use when a sale needs to be cancelled before the batch closes. This is always preferable to a refund for same-day cancellations — faster and fee-free. Do NOT use after settlement — send a Refund instead.

### Implementation notes

1. Reversal only works on the current open batch. Once the batch closes (auto or manual), only a refund is possible.
2. Full amount only — partial reversals are a separate operation (`partial-reversal`), supported only on TSYS US.
3. The original terminal must be connected. The reversal is sent to the same terminal that processed the original sale.
4. For Interac card transactions (TNS / TSYS + TNS): the only post-sale operation available is VOID (card must be present). Show a VOID button, not Refund or Reverse, for Interac transactions in your UI.

:::note PAYSAFE
Paysafe uses TSYS + TNS routing infrastructure. MOTO, partial reversal, and pre-authorization are not available. Tip adjustment forthcoming. Tokenization: single-use Paysafe token — requires merchant onboarding by Paysafe/Handpoint before use. Interac transactions follow TNS void-only rules — see Interac VOID guide.
:::

## Paysafe Token

### What this does
When a card-present sale is processed through Paysafe, Handpoint returns a **Paysafe single-use token** in the transaction result. This token represents the card used at the terminal and can be submitted to Paysafe's Token Vault to create a reusable card-on-file token for future card-not-present (eCommerce) charges — without requiring the cardholder to re-enter their card details online.

This bridges card-present and eCommerce flows: a merchant can onboard a customer in person, store their card details securely in Paysafe's vault, and use the stored token for subsequent online charges (subscriptions, top-ups, deferred billing, etc.).

### When to use it
- Subscription or membership businesses that take the first payment in-person and charge recurring online
- Marketplaces that want to register a card on file after a POS transaction
- Any flow where a card-present sale should also authorise future card-not-present charges

### Requirements
- Merchant must be onboarded for the Paysafe Token Vault by Paysafe and Handpoint — contact your Handpoint integration manager to enable this.
- The token is single-use: it must be exchanged with Paysafe's Token Vault API immediately after the sale to create a reusable multi-use token.
- Standard Paysafe card-present onboarding is required in addition to Token Vault enablement.

### Implementation notes

1. Process a standard card-present sale as normal — no extra parameters needed on the Handpoint side.
2. Inspect the `TransactionResult` for the `paysafeToken` field — this is the single-use token issued by Paysafe.
3. Submit that token to the [Paysafe Token Vault API](https://developer.paysafe.com/en/payments/token-vault/) to create a reusable `paymentHandleToken`.
4. Store the `paymentHandleToken` against the customer record — use it for all future eCommerce charges via Paysafe's Payments API.
5. Tokens expire if not exchanged promptly — perform the Token Vault call synchronously in your `endOfTransaction` / result callback.

### Paysafe Token Vault exchange (outline)

Once you have the single-use token, exchange it with Paysafe's Token Vault to create a stored card-on-file:

```http
POST https://api.paysafe.com/paymenthub/v1/customers/{customerId}/paymenthandles
Authorization: Basic YOUR_PAYSAFE_API_KEY
Content-Type: application/json

{
  "merchantRefNum": "customer-card-001",
  "paymentType": "CARD",
  "singleUseCustomerToken": "<paysafeToken from Handpoint result>",
  "billingDetails": { ... }
}
```

The response includes a `paymentHandleToken` — store this and use it for all future card-not-present charges. Refer to [Paysafe's Token Vault documentation](https://developer.paysafe.com/en/payments/token-vault/) for the full API reference and authentication setup.
