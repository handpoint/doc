## Sale

### What this does
Authorises and captures a card-present payment in a single step.

### When to use it
Use for standard retail and hospitality transactions where the cardholder is present and the amount is known before the transaction starts. Do NOT use when the final amount may change after authorisation — use Pre-Authorization instead.

### Implementation notes

1. The terminal handles EMV chip, contactless, and magnetic stripe automatically — you do not specify the card entry method.
2. The SDK returns an `OperationStartResult` synchronously with a `transactionReference`. The actual result arrives asynchronously via the events listener/callback.
3. Always store the `transactionReference` immediately — you need it for any subsequent reversal.
4. Amount is in the smallest currency unit (cents/pence). `1000` = $10.00 USD.

:::note VANTIV (Worldpay)
Also known as Worldpay. Card-present only — MOTO is not supported (viscus-vantiv returns BAD_REQUEST for all MOTO operations).
:::

## Refund

### What this does
Returns funds to a cardholder's account, either linked to a specific original transaction or as a standalone credit.

### When to use it
Use for returning goods or services after settlement has occurred. For cancellations before settlement, use Reversal instead — it is faster and does not incur interchange fees. Partial refunds (amount less than original) are supported at the protocol level for all acquirers.

### Implementation notes

1. **Linked refund** (recommended): includes `originalTransactionReference` — the gateway validates the original transaction and caps the refund at the original amount plus any tip.
2. **Unlinked refund**: omit `originalTransactionReference` — sends a standalone credit. Some acquirers restrict unlinked refunds; check your acquirer agreement.
3. Amount is in the smallest currency unit. Partial refund: set `amount` less than the original transaction amount.
4. The cardholder's card must be present for card-present refunds.

:::note VANTIV (Worldpay)
Also known as Worldpay. Card-present only — MOTO is not supported (viscus-vantiv returns BAD_REQUEST for all MOTO operations).
:::

## Reversal

### What this does
Voids a sale before settlement, returning the full authorised amount to the cardholder without incurring interchange fees.

### When to use it
Use when a sale needs to be cancelled before the batch closes. This is always preferable to a refund for same-day cancellations — faster and fee-free. Do NOT use after settlement — send a Refund instead.

### Implementation notes

1. Reversal only works on the current open batch. Once the batch closes (auto or manual), only a refund is possible.
2. Full amount only — partial reversals are a separate operation (`partial-reversal`), supported only on TSYS US.
3. The original terminal must be connected. The reversal is sent to the same terminal that processed the original sale.
4. For Interac card transactions (TNS / TSYS + TNS): the only post-sale operation available is VOID (card must be present). Show a VOID button, not Refund or Reverse, for Interac transactions in your UI.

:::note VANTIV (Worldpay)
Also known as Worldpay. Card-present only — MOTO is not supported (viscus-vantiv returns BAD_REQUEST for all MOTO operations).
:::

## Tip Adjustment

### What this does
Modifies the tip amount on a completed sale before batch close.

### When to use it
Use in restaurant/hospitality flows where the cardholder adds a tip after the initial transaction is approved. Do NOT use after batch close — send a Refund for the difference instead.

### Implementation notes

1. **To void a tip:** send `tipAmount: 0`. There is no separate cancel call. The last value sent always wins.
2. **Deadline:** before batch close. For TSYS, auto-close is typically 11pm EST. After close, only a refund is possible.
3. **No card required.** The terminal must be connected and idle. The cardholder does not need to be present.
4. **Math:** the cardholder is charged `original_sale_amount + tip_amount` at settlement. Tip adjustment does not replace the original transaction amount.
5. **Back-office path works cross-SDK:** a sale made via Android SDK can have its tip adjusted via REST API. The integration path used for the sale does not constrain the tip adjustment path.
6. **TMS enablement** is set during onboarding by the Handpoint team. Integrators cannot check or enable this via API — contact your Handpoint integration engineer.
7. iOS HiLite does not support card-present tip adjustment. Use REST API.

:::note VANTIV (Worldpay)
Also known as Worldpay. Card-present only — MOTO is not supported (viscus-vantiv returns BAD_REQUEST for all MOTO operations).
:::

## Pre-Authorization

### What this does
Places a hold on funds without capturing them, allowing the final amount to be adjusted before settlement.

### When to use it
Use for hotel check-ins, car rentals, or any flow where the final amount is unknown at the time of card interaction. Do NOT use for standard retail — use Sale instead.

### Pre-Auth is a bundle of operations

Supporting pre-auth means supporting the full lifecycle:

| Operation | Description |
|---|---|
| **Create** | Place the initial hold |
| **Increase / Decrease** | Adjust the held amount before capture |
| **Capture** | Finalise and charge the held amount |
| **Void hold** | Release the hold without charging (pre-capture) |
| **Capture Reversal** | Cancel a completed capture (pre-settlement) — see separate section; coming soon on TSYS |

### Implementation notes

1. A pre-auth creates an authorisation hold on the cardholder's account. Funds are not captured until you send a Capture.
2. The hold typically expires after 7–30 days depending on the card network and issuer. Always capture or void before expiry.
3. Increase / Decrease adjusts the amount before capture. Supported wherever pre-auth is supported.
4. Always void unused pre-authorisations — unreleased holds affect the cardholder's available credit.
5. **Capture Reversal** (voiding after capture, pre-settlement) is a separate capability, currently in development for TSYS only.

:::note VANTIV (Worldpay)
Also known as Worldpay. Card-present only — MOTO is not supported (viscus-vantiv returns BAD_REQUEST for all MOTO operations).
:::

### Pre-Authorization Capture

Captures the funds from a previously created pre-authorization (completion).

**When to use:** When you know the final amount and are ready to settle. Send the actual charged amount — it may differ from the original pre-auth amount.

**Implementation notes:**
1. The capture amount can be less than the pre-auth amount. Most acquirers also allow a small overage (check your acquirer rules).
2. You must capture before the hold expires (typically 7–30 days).
3. After capture, a standard refund process applies if the cardholder requests a return.
