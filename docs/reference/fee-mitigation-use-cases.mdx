# Fee Mitigation Use Cases

This page lists each case with its amounts. Read [Fee Mitigation](fee-mitigation.mdx) first for the
contract, the fields and the calculation rule.

**Rule for every row:** the gateway only receives amounts. It reads the funding type (credit, debit
or prepaid), and it keeps or removes `fee.amount` and `fee.taxOnFee`. It never calculates a
percentage, a tax or a rounding.

## How to read the tables

| Symbol | Meaning | Comes from | Wire field |
|---|---|---|---|
| `B` | Base amount, before tax, tip and fee | Your application | `amount` |
| `T` | Tip | Your application, or the terminal, before the card read | `tipAmount` |
| `R` | Tax rate | Your tax engine, or the `taxRate` setting | Not sent |
| `X` | Tax on the base, `round(B × R)` | Your application | Part of `taxAmount` |
| `P` | Fee percentage | `surchargePercent`, or the admin fee setting | Not sent |
| `fee` | `round(fee base × P)`, or the fixed amount | The SDK, or your application | `fee.amount` |
| `taxOnFee` | `round(fee × R)` for a `_TAXED_FEE` value, else 0 | The SDK, or your application | `fee.taxOnFee` |
| Total | `B + T + X + taxOnFee + fee` | The SDK, or your application | The request total |

All amounts are decimals with two places, rounded once with `HALF_UP`.

The data in every table is the same, so you can compare the rows: `B` = 100.00, `T` = 15.00 (only
where a row says so), `R` = 10% so `X` = 10.00, and `P` = 3%.

### What the numbers mean

| Question | Answer | Example |
|---|---|---|
| What does the fee base change? | Only how `fee` is calculated. It never changes what is added to the total. Each part (base, tip, tax) is added once | A fee base of `B + X` = 110.00 gives a fee of 3.30. The tax of 10.00 is still added once |
| Is base + tip + fee the total? | No. The tax is missing | 100.00 + 15.00 + 3.45 = 118.45 is not the total. The total is 100.00 + 15.00 + 10.00 + 3.45 = 128.45 |
| When the fee is taxed, is the tax 10% of the fee, or 10% of base plus fee? | 10% of base plus fee. It is one tax in two parts | Tax on the base 10.00 + tax on the fee 0.30 = 10.30 |
| What is `taxOnFee`? | The part of the total tax that exists only because the fee exists. It is not another tax | `taxOnFee` = 0.30. `taxAmount` = 10.30 |
| Why is it separate? | If the gateway removes the fee on a debit card, it must also remove those 0.30. Otherwise the customer pays tax on a fee that was not charged | Debit: authorized = 113.30 − 3.00 − 0.30 = 110.00 |
| Is `feeCalculation` the same as `taxOnFee`? | No. `feeCalculation` is the rule. `taxOnFee` is the result. Only the result goes to the gateway | A `_TAXED_FEE` value with a tax rate of 0 gives `taxOnFee` = 0 |

## Surcharge

Credit cards only. All six `feeCalculation` values are valid.

| ID | Value | Card | `fee.amount` | `taxOnFee` | `taxAmount` | Total | Gateway result |
|---|---|---|---|---|---|---|---|
| SC-1 | `FEE_ON_BASE` | Credit | 3.00 | 0.00 | 10.00 | 128.00 | Fee kept. `reason` is `APPLIED` |
| SC-2 | `FEE_ON_BASE_TAX` | Credit | 3.30 | 0.00 | 10.00 | 128.30 | Fee kept |
| SC-3 | `FEE_ON_BASE_TIP` | Credit | 3.45 | 0.00 | 10.00 | 128.45 | Fee kept |
| SC-4 | `FEE_ON_BASE_TIP_TAX` | Credit | 3.75 | 0.00 | 10.00 | 128.75 | Fee kept |
| SC-5 | `FEE_ON_BASE_TAXED_FEE` | Credit | 3.00 | 0.30 | 10.30 | 128.30 | Fee kept. Receipt order: base, tip, fee, tax |
| SC-6 | `FEE_ON_BASE_TIP_TAXED_FEE` | Credit | 3.45 | 0.35 | 10.35 | 128.80 | Fee kept. Waits for confirmation, see [Pending decisions](fee-mitigation.mdx#pending) |
| SC-7 | Any of SC-1 to SC-6 | Debit | As its row | As its row | As its row | As its row | Fee dropped. Authorized = total − fee − `taxOnFee` = 125.00 in all six rows. `reason` is `NOT_ELIGIBLE_DEBIT` |
| SC-8 | Any | Prepaid | As its row | As its row | As its row | As its row | Fee dropped. Authorized 125.00. `reason` is `NOT_ELIGIBLE_PREPAID` |
| SC-9 | Any | Debit card, customer presses "credit" | | | | | Fee dropped. The card type decides, not the button |
| SC-10 | Any | The customer refuses the fee | None | 0.00 | 10.00 | 125.00 | Your application sends the sale with no `fee` |
| SC-11 | Any | Credit card, partial approval enabled | As its row | | | | The acquirer receives "partial approval not allowed" for this transaction. See [Partial approval](fee-mitigation.mdx#partial-approval) |
| SC-12 | Any | Credit card, remote sale (MOTO) | As its row | | | | Allowed only after the operator states the amount and the customer can cancel |
| SC-13 | SC-3, SC-4 or SC-6 | Tip added after the authorization | | | | | A tip adjustment carries no fee. The fee on that tip is not collected |

With no tip (`T` = 0), the values give: `FEE_ON_BASE` 113.00, `FEE_ON_BASE_TAX` 113.30 and
`FEE_ON_BASE_TAXED_FEE` 113.30 (fee 3.00, `taxOnFee` 0.30). The tip values give the same result as
their value without a tip.

## Dual pricing

The fee is inside the card price. A tip is not allowed.

| ID | Value | Card | `fee.amount` | `taxOnFee` | Total | Gateway result |
|---|---|---|---|---|---|---|
| DP-1 | `FEE_ON_BASE` | Credit | 3.00 | 0.00 | 113.00 | Fee kept |
| DP-2 | `FEE_ON_BASE` | Debit | 3.00 | 0.00 | 113.00 | Fee kept. A debit card pays the card price |
| DP-3 | `FEE_ON_BASE_TAX` | Credit | 3.30 | 0.00 | 113.30 | Fee kept |
| DP-4 | `FEE_ON_BASE_TAXED_FEE` | Credit | 3.00 | 0.30 | 113.30 | Fee kept |
| DP-5 | Any | Any | With `tipAmount` | | | Rejected. A tip is not allowed |

The cash price in these rows is 110.00.

:::note A cash price for debit cards is an option
Handpoint offers it to integrators that need it: a debit card pays the cash price. The
`fee.paymentPath` field carries that choice. Its exact values wait for a decision. See
[Pending decisions](fee-mitigation.mdx#pending). Do not build against `paymentPath` yet.
:::

## Cash discount

The card flow carries no fee. The listed price is the card price. The `feeCalculation` value only
calculates the discount that your application shows.

| ID | Value | Flow | Discount | Total | Gateway result |
|---|---|---|---|---|---|
| CD-1 | `FEE_ON_BASE` | Card | 3.00 on `B` | 110.00 (listed price) | A normal sale. The SDK removes `fee` before the call. A `fee` that reaches the gateway returns error `4272` |
| CD-2 | `FEE_ON_BASE_TAX` | Card | 3.30 on `B + X` | 110.00 | Same as CD-1 |
| CD-3 | `FEE_ON_BASE` | Cash | 3.00 | 106.70 (tax recalculated on 97.00 = 9.70) | No gateway call |
| CD-4 | Any | The customer cancels at the SDK dialog | | | The transaction is cancelled with a reason. No receipt |

## Admin fee

Every tender. The gateway never drops it.

| ID | Mode and value | Card | `fee.amount` | `taxOnFee` | `taxAmount` | Total | Gateway result |
|---|---|---|---|---|---|---|---|
| AF-1 | `PERCENT` 2%, `FEE_ON_BASE` | Credit or debit | 2.00 | 0.00 | 10.00 | 112.00 | Fee kept |
| AF-2 | `PERCENT` 2%, `FEE_ON_BASE_TAXED_FEE` | Credit or debit | 2.00 | 0.20 | 10.20 | 112.20 | Fee kept |
| AF-3 | `FIXED` 5.00, `FEE_ON_BASE` | Credit or debit | 5.00 | 0.00 | 10.00 | 115.00 | Fee kept |
| AF-4 | `FIXED` 5.00, `FEE_ON_BASE_TAXED_FEE` | Credit or debit | 5.00 | 0.50 | 10.50 | 115.50 | Fee kept |
| AF-5 | Any | Cash | Same fee | | | Same total | The fee applies to cash as well. Without this, it is a card surcharge in disguise |
| AF-6 | Any | The customer refuses at the dialog | None | | | | A sale with no `fee`, or a cancel |

## Operations

Does the request carry a fee?

| Operation | Fee | What happens |
|---|---|---|
| Sale | Yes | See the tables above |
| Remote sale (MOTO) | Per program | The operator states the amount. The customer can cancel |
| Pre-authorization | No | A `fee` is rejected |
| Capture of a pre-authorization | Yes | A surcharge or an admin fee is allowed, because the capture sets the amount the customer pays. Dual pricing is not |
| Increase | No | A `fee` is rejected |
| Decrease | No | Send the reduced total, with the reduced fee inside it |
| Tip adjustment | No | The tip is added with no fee. A fee on that tip is not collected |
| Refund | No | You prorate the fee. See the example below |
| Refund of a sale whose fee was dropped (debit) | No | There is no fee to return. Do not add one |
| Reversal | Automatic | It carries the amount that was authorized. A dropped fee is not reversed |
| Card verification (zero amount) | No | No fee and no tax |

A fee sent with an operation marked "No" is rejected. It is never removed without a message.

:::note An increase carries no fee yet
Whether a surcharge can apply on an increase is a pending decision. See
[Pending decisions](fee-mitigation.mdx#pending).
:::

**Refund example.** A customer paid 125.00 plus a fee of 3.00. The merchant refunds half the goods,
which is 62.50. The fee returned is `round(3.00 × 62.50 ÷ 125.00)` = 1.50. The refund amount you send
is **64.00**.

## Edge cases

| ID | Case | Result |
|---|---|---|
| X-1 | A state or territory prohibits a surcharge | The Console does not let the merchant enable the program there |
| X-2 | `surchargePercent` is above the permitted maximum | The Console and the SDK reject it. The gateway does not check the rate |
| X-3 | The merchant enables a surcharge before the notice period ends | The Console blocks it |
| X-4 | Two programs on one location | The Console blocks it. A transaction carries one program |
| X-5 | A `_TAXED_FEE` value and no tax rate | The SDK rejects the configuration. With a tax rate of 0, `taxOnFee` is 0 |
| X-6 | The base has no tax (`X` = 0) | `taxOnFee` follows the tax rule of the fee, not of the base. If the fee is not taxable, `taxOnFee` is 0. If the fee is taxable, `taxOnFee` is `round(fee × R)`, and it is the only tax. The gateway only checks that `taxOnFee` is not above `taxAmount` |
| X-7 | Mixed tax rates in one cart | Your application uses one rate for the tax on the fee. The rate is not decided for this case |
| X-8 | The tip changes after the fee was calculated | Calculate again before the card read. After the read, the amount is fixed |
| X-9 | `taxOnFee` is above `taxInformation.taxAmount` | Rejected with error `4269` |
| X-10 | `fee.amount` is missing | `FEE_AMOUNT_MISSING` |
| X-11 | The program is not enabled for the merchant | `PROGRAM_NOT_ENABLED` |
| X-12 | The customer cancels at a fee dialog | The transaction is cancelled with a reason. No gateway call |
| X-13 | The fee dialog times out | The transaction is cancelled with the reason `TIMEOUT`. The time is not decided |
| X-14 | Partial approval and a fee | See SC-11 |
| X-15 | Rounding: the parts differ by one cent from the rounded sum | Round each part once. Add the rounded parts |
| X-16 | An acquirer other than EPI | Not supported |
| X-17 | A second partial refund | The fee returned in all refunds cannot be more than the original fee. The last refund takes the remaining cents |
| X-18 | The chip signs the amount before the funding type is known | A surcharge on a debit card can be charged. This is open. Dual pricing avoids it, because the price is chosen first |
| X-19 | A merchant asks for a taxed fee on `B + X` | Not offered. The tax needs the fee, and the fee would need the tax |
| X-20 | A fee sent with an operation that carries none | Rejected |
