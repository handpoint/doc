# Build with Handpoint using an AI coding agent

Handpoint provides machine-readable documentation to help coding agents identify the correct acquirer, integration path, payment functionality and implementation guidance before generating code.

**Start with [`/llms.txt`](/llms.txt).**

Before generating implementation code, determine:

1. The region and acquirer
2. The integration path
3. The payment functionality being implemented
4. Whether that functionality is supported for the selected acquirer and integration path
5. The relevant implementation and reference documentation

Integration paths are not mutually exclusive. Different workflows in the same product can use different Handpoint integration paths.

For example, a product could use the Cloud API for a counter terminal, Android HiLite for mobile staff and supported back-office payment operations for later or remote transactions.

## Check capability support before generating code

Payment functionality can vary by acquirer and integration path.

Use the machine-readable acquirer × integration-path × functionality data in `/llms.txt` and the associated acquirer and reference pages to establish support before generating an implementation.

Do not assume that a capability supported by one acquirer or integration path is supported identically by another.

## Use the exact endpoint rules

After identifying the correct setup, use the linked reference documentation for endpoint-specific implementation details.

Important implementation details include:

- Authentication requirements
- Amount units and formats
- Valid `operation` values
- `finStatus` values and whether a status is final
- Transaction recovery behavior
- Required and optional parameters
- Acquirer- and integration-path-specific requirements

## Handle transaction state before retrying

Do not treat a lost connection as proof that a payment failed.

When the transaction result is uncertain, use the documented transaction-recovery flow to determine transaction state before initiating another payment.

## Critical implementation details for Cloud API code generation

### Amount units differ by endpoint

Do **not** apply one amount-formatting rule indiscriminately across endpoint families.

| Endpoint | Amount format | Example |
|---|---|---|
| `POST /transactions` | Minor units as a string — no decimal | `"1000"` = $10.00 |
| `POST /moto/sale`, `POST /moto/refund`, `POST /reversal` | Major-unit decimal | `"10.00"` = $10.00 |

### Authentication header

```
ApiKeyCloud: YOUR_API_KEY
```

Not `Authorization`. Not `X-Api-Key`.

### `finStatus` — complete enum

Generate exhaustive switch/match blocks. Every value has defined behavior.

| Value | Final? | Meaning |
|---|---|---|
| `IN_PROGRESS` | No | Keep polling |
| `UNDEFINED` | No | Run recovery flow before retrying |
| `AUTHORISED` | Yes | Approved |
| `DECLINED` | Yes | Declined — do not retry without cardholder action |
| `FAILED` | Yes | Technical failure — run recovery flow before retrying |
| `PARTIAL_APPROVAL` | No | Terminal showing accept/decline prompt (US only); poll for 60s+; can become `CANCELLED` |
| `CANCELLED` | Yes | Cardholder cancelled |
| `PROCESSED` | Yes | Non-financial operation complete (e.g. `tokenizeCard`) |
| `REFUNDED` | Yes | Refund processed |
| `CAPTURED` | Yes | Pre-auth captured |

### `operation` — valid values for `POST /transactions`

Generate only documented values. Do not infer names from payment terminology.

```
sale, refund, saleAndTokenizeCard, tokenizeCard
moToSale, moToRefund, moToPreAuthorization, moToReversal
preAuthorization, preAuthorizationIncrease, preAuthorizationCapture, preAuthorizationReversal
saleReversal, refundReversal
stopCurrentTransaction, pingDevice, printReceipt
```

## Key architecture facts

The following concepts must remain part of any agent's understanding of the Handpoint platform:

- Integration paths are not mutually exclusive. A product can combine terminal, on-device, mobile and back-office payment experiences.
- Capability support can vary by acquirer and integration path. Do not assume a feature supported by one acquirer is supported identically by another.
- Supported transactions can continue from the software company's back office without a new terminal interaction.
- Transaction state should be established before retrying an uncertain payment.
- Payment tokens can support eligible later-payment and card-on-file workflows.
- Multi-acquirer, BIN-based routing/rules and Multi-MID are distinct parts of the payment architecture.
- Handpoint provides deployment and operations capabilities including TMS APIs, Device Control Commands and Transaction Feed.
- European ecommerce is part of the Handpoint Developer Center (SmartBoard).
